# 产品需求文档 (PRD) - 不鸽令同城低成本组局平台

> 当前主 PRD。
>
> 这份文档描述的是升级后的整个平台，不再只是“线下契约引擎”。原先的押金、信用、自动仲裁、投诉和核销能力，已经被并入本文的“底层履约机制”章节。

**产品版本：** v2.0  
**产品定位：** 同城低成本组局平台  
**产品结构：** 表层组局产品 + 底层线下契约引擎  
**一句话价值：** 让用户更容易发起低成本活动，也更放心和陌生人线下成局

---

## 1. 产品定位

### 1.1 一句话定位

发现附近低成本玩法，快速发局，安心成局。

### 1.2 产品定义

`不鸽令` 是一个基于 LBS 的 UGC 轻组局平台。

平台不主打“聊天”，而是主打：

1. 用户可快速发起一个低成本活动
2. 附近的人可以报名参加
3. 系统通过服务费、保证金、信用和签到机制降低爽约风险
4. 活动结束后沉淀战报，并支持一键发起同款

### 1.3 两层结构

当前产品必须按两层理解：

- 表层产品：同城低成本组局平台
- 底层能力：线下契约引擎

用户看到的是模板、卡片流、签到、评价、战报和同款复用。真正保证平台不失控的，是底层的押金履约、信用体系、内容安全、投诉仲裁和资金结算。

## 2. 用户问题与市场机会

### 2.1 用户问题

目标用户面对的不是“没有社交软件”，而是“没有合适的低成本线下活动工具”。

常见问题：

- 想出门，但不知道去哪
- 不想一个人待着，但也不想进入强社交场景
- 想找附近的人一起散步、便利店坐坐、便宜吃饭、公园发呆
- 预算低，不愿意参加高客单价活动
- 又担心陌生人放鸽子、临时变卦、现场风险

### 2.2 市场空白

| 类型 | 典型问题 |
|------|----------|
| 陌生人社交 App | 容易滑向尬聊、相亲、骚扰、诈骗 |
| 活动平台 | 太重，太贵，组织门槛高 |
| 本地生活平台 | 更偏消费，不偏组局 |
| 微信群 | 能拉人，但信用弱、沉淀弱、复用弱 |
| 内容平台 | 有灵感，没有就地成局能力 |

### 2.3 机会判断

机会不在于再做一个社交软件。

机会在于，把：

- 附近的人
- 低成本内容灵感
- 可执行的活动模板
- 能约束爽约的履约机制

放进同一个产品里。

## 3. 产品目标

### 3.1 MVP 核心目标

验证以下 5 件事：

1. 用户是否愿意发起低成本组局
2. 用户是否愿意参加陌生人发起的低成本组局
3. 服务费 + 保证金是否能有效降低爽约
4. 活动评价与信用是否能提升线下安全感
5. 战报与同款复用是否能带来二次供给

### 3.2 中期目标

- 提高活动供给密度
- 提高成局率
- 提高复购率和复发率
- 沉淀可信发起人和可信参与者
- 建立“内容灵感 → 活动战报 → 同款复用”的增长飞轮

### 3.3 长期目标

成为一个：

- 适合年轻人低成本出门
- 不依赖重聊天
- 有明确履约约束
- 可持续沉淀本地活动内容

的同城活动平台。

## 4. 用户画像

### 4.1 低预算年轻人

- 18-28 岁
- 学生、初入职场、自由职业者
- 预算低，但不想总宅着

需求：

- 0-50 元内也能出门
- 不需要高投入准备
- 最好附近就能成局

### 4.2 轻社交人群

- 不喜欢高压社交
- 不想长聊，不想复杂关系
- 更喜欢“一起做点事”，而不是“先聊天再说”

需求：

- 有场景，有理由见面
- 不必深度绑定
- 能安全退出

### 4.3 活动发起型用户

- 有表达欲
- 愿意带头组织
- 讨厌自己拉群、挨个催人、现场被放鸽子

需求：

- 快速发起
- 更容易成局
- 履约规则明确

### 4.4 内容消费型用户

- 平时刷短视频、小红书、同城内容
- 看见别人“便宜又有趣”的玩法会想模仿

需求：

- 能一键复用
- 不想从零组织

## 5. 产品边界

### 5.1 产品是

- 同城低成本组局工具
- 活动驱动的轻社交平台
- 附近活动撮合小程序
- 有履约机制的 UGC 活动平台

### 5.2 产品不是

- 不是陌生人聊天 App
- 不是相亲平台
- 不是陪玩/陪聊平台
- 不是高客单价活动平台
- 不是私密空间见面工具

### 5.3 调性要求

产品必须强调：

- 低成本
- 公共空间
- 轻量、弱关系
- 不强制消费
- AA 或明确预算
- 安全优先

---

## 6. MVP 范围

### 6.1 必做能力

- 模板化发起活动
- 首页附近活动流
- 结构化详情页
- 报名支付：服务费 + 保证金
- 最低成局人数 + 自动成局
- 定位签到为主，扫码/人工确认为辅
- 活动后互评
- 信用信息沉淀
- 活动战报生成
- 从战报发起同款

### 6.2 暂不做

- 完整 IM 群聊
- 一对一私聊
- 高客单价活动
- 商家后台
- 复杂推荐算法
- 多城市重运营后台

---

## 7. 核心用户路径

### 7.1 发起人路径

1. 选择模板
2. 填时间、地点、人数、安全开关
3. 发布活动
4. 等待用户报名并自动成局
5. 活动当天查看签到状态
6. 活动结束后查看互评和战报
7. 持续复用自己的活动模板或战报

### 7.2 参与者路径

1. 浏览附近活动流
2. 进入详情页判断是否值得参加
3. 支付服务费 + 保证金报名
4. 活动当天签到或出示补充核验凭证
5. 活动结束后评价
6. 查看历史活动和战报

### 7.3 内容复用路径

1. 用户进入活动战报页
2. 看到模板、人均预算、人数、集合方式、安全配置
3. 点击“发起同款”
4. 系统自动带入模板、费用和条件
5. 用户只改时间地点，重新发布

这条路径是增长闭环关键。

## 8. 核心功能模块

### 8.1 附近活动流

首页卡片至少展示：

- 活动标题
- 模板类型
- 时间
- 距离
- 当前人数 / 成局线 / 人数上限
- 预算
- 服务费 + 保证金
- 安全标签
- 发起人信用概览

目标：

- 让用户 3 秒内判断值不值得点开

### 8.2 模板化发起

发起页不是传统空白表单。

它应该优先提供：

- 模板类型
- 默认标题/摘要
- 推荐预算
- 推荐人数
- 安全默认项

目标：

- 降低发起门槛
- 控制活动质量
- 让活动更可分发、更可复用

### 8.3 详情页与报名页

详情页需要讲清楚：

- 这是什么局
- 需要花多少钱
- 几个人才成局
- 何时截止报名
- 如何签到
- 哪些安全条件已经开启

报名页必须把费用结构和规则说明清楚，减少“先报再后悔”。

### 8.4 自动成局与签到

活动不再完全依赖发起人手动审批。

平台需要支持：

- 达到最低人数自动成局
- 到截止时间自动锁局
- 活动开始前开放签到
- 定位签到为主流程
- 扫码/手动确认作为补充流程

### 8.5 互评与信用

活动结束后应引导互评：

- 正向标签
- 负向标签
- 可选一句话评价

评价结果反哺：

- 用户信用分
- 详情页信任感
- 风控判断

### 8.6 战报与同款复用

战报页至少要沉淀：

- 活动标题
- 模板类型
- 人数与到场率
- 预算与费用结构
- 集合方式
- 氛围/安全标签
- 一句话总结

战报不是终点。

它必须承担“复用供给”的职责，也就是让其他用户可以直接发起同款。

## 9. 信任、安全与平台边界

### 9.1 风控原则

- 公共空间优先
- 风险高于增长
- 结构化规则优先于事后人工处理
- 不鼓励脱离平台过早私聊

### 9.2 高风险场景限制

MVP 默认不鼓励或需严格审核的场景：

- 私宅见面
- 深夜高风险活动
- 酒吧/KTV 等高灰度场景
- 一对一私密约见
- 强消费绑定局

### 9.3 投诉与兜底

平台必须支持：

- 举报
- 图片存证
- LBS 存证
- 自动仲裁
- 人工补充处理极端案例

## 10. 底层履约机制（继承自线下契约引擎）

这一章不是附属内容，而是整个平台能成立的基础。

### 10.1 服务费与保证金双金额结构

表层产品讲“低成本组局”，底层不能没有明确的履约约束。

当前资金结构：

- 服务费：平台收入，用于覆盖撮合与系统成本
- 保证金：履约约束工具，用于签到后退回或异常时扣保/补偿

兼容原因：

- 旧系统只有 `depositTier`
- 新系统升级为 `serviceFee + bondAmount`
- 为了平滑演进，代码中两种语义会并存一段时间

### 10.2 履约成功与退款

履约成功后：

- 保证金应原路退回
- 用户信用获得正向积累
- 活动进入后续评价和战报阶段

原先“扫码核销后立即退款”的机制仍然保留，但现在应理解为底层能力，而不是唯一主流程。

### 10.3 违约补偿与分账

底层仍保留旧引擎的核心思想：

- 履约成功，用户拿回保证金
- 违约时，不是简单吞掉钱，而是按规则处理

旧机制中的“3/7 分账补偿”可以继续作为底层异常处理能力，用于：

- 爽约扣保
- 发起人补偿
- 平台成本覆盖

### 10.4 签到、扫码与补充核验

当前产品主流程应是：

- 定位签到

但底层仍保留：

- 动态二维码
- 发起人扫码核验
- 手动确认到场

这些机制的价值在于：

- 当定位失败时兜底
- 当用户手机权限异常时兜底
- 当现场争议出现时补充证据

### 10.5 微信号与社交解锁

旧引擎里，微信号解锁是关键主流程。

在新平台里，这个逻辑被降级为补充手段：

- 主目标不再是“尽快私聊”
- 主目标是“围绕活动完成线下成局”

所以微信号解锁可以保留，但不应成为平台核心心智。

### 10.6 信用分与访问控制

底层信用体系继续保留，并升级为平台级信任资产。

至少承担 3 个职责：

1. 访问控制
2. 活动信任展示
3. 风控输入

旧规则里有价值的部分继续保留：

- 初始信用分
- 履约加分
- 爽约扣分
- 举报成立重扣
- 低信用限制发起
- 极低信用禁止使用

### 10.7 自动仲裁

自动仲裁仍然是底层引擎最关键的护城河之一。

平台需要在以下场景自动给出规则化处理：

- 参与者未到场
- 发起人未到场
- 双方均未到场
- 双方均在场但未完成补充核验

原则：

- 优先使用结构化规则
- 尽量减少人工客服介入
- 但为极端投诉场景保留人工处理入口

### 10.8 举报、投诉与存证

底层需要持续支持：

- 举报入口
- 图片上传
- LBS 存证
- 冻结与复核

这部分是表层平台“敢做陌生人低成本组局”的前提。

### 10.9 日历、历史与信用资产

旧引擎里的活动日历和海报能力，在平台里仍然重要。

它们现在不只是“守约纪念品”，而是：

- 历史活动记录
- 可信出门轨迹
- 信用可视化资产
- 后续复购与分享素材

---

## 11. 核心指标

MVP 阶段建议重点看：

- 活动发布量
- 活动成局率
- 报名支付转化率
- 到场率
- 爽约率
- 活动后评价率
- 战报生成率
- 同款复用率

如果“战报生成了但没人复用”，说明增长闭环还没真正成立。

---

## 12. 非目标

当前阶段不追求：

- 做重社交关系链
- 做强聊天产品
- 做高客单价精品活动平台
- 做商家主导活动平台
- 做复杂内容社区

平台最重要的，是先把：

模板发起 → 报名成局 → 签到评价 → 战报复用

这条闭环跑顺。

---

## 13. 结论

`不鸽令` 的产品升级，不是给旧押金工具外面包一层新文案。

真正的变化是：

- 表层变成了一个更容易产生供给和复用的低成本组局平台
- 底层仍然坚持用契约、支付、信用、投诉和仲裁来约束线下风险

这两层一起，才是当前平台的完整产品定义。

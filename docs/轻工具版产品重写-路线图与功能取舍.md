## Problem Statement

之前的产品规划虽然有逻辑，但整体偏“活动平台化”和“履约系统化”。它更强调流程完整、状态闭环、到场确认、评价沉淀和管理能力。

这套思路的问题不是错，而是太重。

对于当前目标用户来说，产品一旦太像“被平台管理的一场正式活动”，就会带来明显的心理阻力：

- 发起变麻烦
- 报名变犹豫
- 参与像在完成任务
- 结束后还要处理额外动作

所以新的核心任务不是继续补流程，而是把产品重新拉回到“轻工具”方向：

**让用户更容易顺手发起一个小局、更容易轻松加入、又不会因为产品太重而被吓跑。**

## Demand Evidence

- 用户场景是低预算、低承诺、低关系压力的小局，而不是正式活动。
- 核心模板本身也说明了这一点：散步、便利店坐坐、公园发呆、低价吃饭、自习搭子。
- 当前收费结构也是轻量的：服务费普遍在 `1.9-3.9 元`，保证金普遍在 `9.9-19.9 元`，更适合“顺手约成”的工具，而不是强组织平台。
- 你的最新判断很关键：评价、签到等功能“设计得太产品化了，不符合用户群体”，这意味着问题已经不是缺功能，而是产品存在感过强。

## Status Quo

当前已有能力里，存在两类东西：

第一类是应该继续保留并强化的：

- 模板化发起
- 附近活动浏览
- 快速加入
- 一键发起同款
- 分享裂变

第二类是应该弱化、隐藏甚至降级的：

- 强制签到
- 强制评价
- 高频提醒
- 重信用体系曝光
- 多层状态流转
- 发起人后台式管理感

这意味着接下来的重写，不是“再加什么功能”，而是：

- 前台更轻
- 主链路更短
- 底层继续兜底
- 异常能力继续存在，但不再主叙事

## Target User & Narrowest Wedge

目标用户不是在寻找“靠谱的活动管理系统”，而是在寻找一种更轻松的方式：

- 快速发个小邀约
- 看看附近有没有同类人
- 少废话，少压力，少被放鸽子

最窄切口仍然建议围绕这几类局：

- 散步瞎逛局
- 便利店坐坐局
- 公园发呆局
- 低价吃饭局
- 自习搭子局

这些模板最符合轻工具逻辑，因为它们：

- 不正式
- 不高消费
- 不需要复杂组织
- 容易临时起意
- 用户更愿意重复使用

## Constraints

- 线下陌生人小局天然存在爽约风险，所以不能完全去掉底层约束。
- 但如果前台约束太强，用户会在转化前就流失。
- 平台当前还在早期，不适合把大量精力放在“流程完整度”而不是“发起和报名轻量化”上。
- 收入模型也决定了不能靠复杂流程去换单次高收入，仍然要依赖高频轻量使用。

## Premises

- “轻”是核心竞争力，不是 UI 风格。
- 规则和风控仍然重要，但应该退到后台。
- 正常用户不应该频繁感受到平台在管理他。
- 用户最宝贵的不是填写能力，而是那一点“我现在想约一下”的冲动。
- 任何会打断这股冲动的设计，都应该被警惕。

## Approaches Considered

### Approach A: 保留重流程，只是优化文案

做法：

- 保留签到、评价、确认、提醒、信用体系，只是把话术说轻一点。

问题：

- 本质没有变
- 用户仍然能感知到“这事很正式”
- 只是把重流程换了个更温和的说法

### Approach B: 重写主链路，底层保留兜底

做法：

- 主流程围绕“发起、浏览、加入、见面、再来一次”
- 约束、争议、风控、异常处理留在底层
- 正常用户尽量少被打扰

优势：

- 更贴近真实使用场景
- 转化阻力更小
- 更符合产品哲学

## Recommended Approach

推荐采用 Approach B。

未来版本不再以“活动平台闭环完整”为目标，而改成下面这条极简主链路：

`看到一个局 -> 感觉还行 -> 顺手加入 -> 到点去见 -> 如果不错就再来一局`

这条链路里的每一环，都应该追求：

- 少操作
- 少判断
- 少压力
- 少被平台教育

## New Product Backbone

轻工具版的产品骨架，建议固定成这 5 个前台核心能力：

### 1. 模板发起

用户不用从零组织，只要选一个感觉对味的模板，补一点时间地点，就能发出邀约。

### 2. 附近浏览

用户先看到“今晚附近有什么小局”，而不是先理解一堆规则。

### 3. 轻量加入

加入动作尽量短，不让用户在付款前后承担太多流程感。

### 4. 顺手成局

重点不是“状态完整”，而是“这个局看起来真能成”。

### 5. 一键再来

活动结束后最重要的动作不是评价，而是“还想不想再来一次”。

## Function Triage

这一轮的目标不是再扩功能，而是给现有能力定去向：

- 前台主体验
- 轻量承接
- 底层兜底
- 直接删减

### A. 保留并前置

这些功能应该成为主体验：

- 模板广场
- 附近活动流
- 差几人成局
- 低预算提示
- 轻费用说明
- 一键发起同款
- 分享卡
- 快速复用常用模板

处理方式：

- 放在首页、详情页、战报页的首屏或强 CTA 区
- 文案只说用户关心的结果，不说系统能力
- 尽量让它们成为“顺手点一下就能继续”的动作

为什么保留：

- 这些能力直接服务“顺手发起 / 顺手加入 / 顺手再来”
- 它们是轻工具的正向骨架，不会显著增加平台感

### B. 保留但降级

这些功能存在，但不要挡住主链路：

- 到场确认
- 历史记录
- 战报
- 信用信号
- 活动前提醒

处理方式：

- 改成轻确认、轻回顾、轻提示
- 默认不强制，不连续打扰，不占首屏
- 只在用户已经接近完成时出现

降级方式：

- 不强制
- 不高频
- 不主视觉
- 只在有帮助时出现

为什么降级：

- 这些功能有用，但一旦前置就会明显变重
- 它们更适合做“结束后的承接”或“必要时的辅助”

### C. 保留但隐藏到底层

这些能力是安全网，不是主卖点：

- 保证金逻辑
- 争议处理
- 举报能力
- 异常仲裁
- 爽约判定
- 风险识别

处理方式：

- 正常用户默认看不到
- 只在异常、争议、风控场景下出现
- 文案尽量从“处罚”转成“补充情况 / 处理问题”

为什么放底层：

- 这些能力必须有，不然产品不稳
- 但它们一旦被主流程感知，就会把产品推回平台化

### D. 应主动删减的重感设计

这些设计如果继续做重，会偏离产品哲学：

- 强制签到闭环
- 强制互评闭环
- 报名后多轮确认
- 多次提醒催促
- 活动管理后台感
- 复杂信用分叙事

建议直接替换成：

- `我到了`
- `再来一次`
- `补充情况`
- `轻提醒一次`

## Functional Triage by Module

下面这一层不再讲原则，直接给模块定去向。

### 1. 前置到主链路

这些功能要放在用户最常看到、最常点到的位置：

- 模板广场
- 附近活动流
- 活动卡片摘要
- 发起页的默认值和快捷发布
- 详情页的核心信息区
- 一键发起同款
- 分享卡
- 快速复用常用模板

保留理由：

- 它们直接服务“看见 -> 想去 -> 顺手加入 / 发起”
- 它们不会天然增加平台感，反而能降低决策成本

### 2. 降级到结束承接

这些功能要有，但只能做轻承接，不要抢首屏：

- 到场确认页
- 战报页
- 历史页
- 个人中心里的最近小局
- 日历页
- 海报页
- 活动前提醒

处理方式：

- 只在用户快结束、准备复用时出现
- 只给一次轻提示，不做连续催促
- 入口放在详情页尾部、战报页、个人中心里

降级理由：

- 这些功能有价值，但很容易把产品从“轻工具”拉回“流程工具”
- 它们更适合作为复购承接，不适合作为第一眼主叙事

### 3. 隐藏到底层兜底

这些能力要保留，但默认不要露给正常用户：

- 保证金逻辑
- 争议处理
- 举报能力
- 异常仲裁
- 爽约判定
- 风险识别
- 核验页
- 扫码核销页

处理方式：

- 平时不出现，异常时才出现
- 文案从“处罚 / 核销 / 审批”改成“补充情况 / 处理问题 / 确认异常”

隐藏理由：

- 它们是必要的安全网
- 但一旦前台可见，就会强烈放大平台感

### 4. 直接删减或替换

这些功能和表达方式，建议从默认主流程里拿掉：

- 强制签到闭环
- 强制互评闭环
- 报名后多轮确认
- 多次提醒催促
- 复杂信用分叙事
- 活动管理后台感
- 公开核销感

替换方向：

- 签到 -> `我到了`
- 互评 -> `这次还顺利吗`
- 管理 -> `这局现在怎么样了`
- 核销 -> 只在兜底场景出现

### 5. 这一轮的优先级顺序

如果只做一轮，顺序建议是：

1. 先保住前置链路，让发起和加入更轻
2. 再把结束承接页做成轻回流
3. 然后把风控和核验藏到底层
4. 最后把所有重感设计从主流程里移出去

## Feature Lock List

下面这一层把具体功能也锁死，后面排期时直接照这个去做。

### 1. 必须保留并前置

- 模板广场
- 附近活动流
- 一键发起同款
- 分享卡
- 快速复用常用模板
- 活动卡片里的时间、地点、花费、差几人成局

结论：

- 这些是轻工具的入口，不该再往后藏
- 它们负责把“我想约一下”变成“我现在就能点”

### 2. 必须保留但明显降级

- 到场确认
- 历史记录
- 战报页
- 个人中心里的最近小局
- 日历页
- 海报页
- 活动前提醒
- 信用信号
- 规则页

结论：

- 这些能力都还有价值，但只能做承接，不做主叙事
- 它们要么放在结束后，要么放在个人空间里，不能压住首页和详情页

### 3. 必须保留但藏到底层

- 保证金
- 争议处理
- 举报
- 异常仲裁

- 核验页

结论：

- 这些是安全网，不是产品心智
- 正常用户不应该感受到它们在主流程里存在

### 4. 应该删减或替换

- 强制签到闭环
- 强制互评闭环
- 报名后多轮确认
- 多次提醒催促
- 活动管理后台感
- 复杂信用分叙事
- 手动审批式报名
- 公开核销感
- 强社交解锁感
- 过重的海报月报表达

替换方向：

- 签到 -> `我到了`
- 互评 -> `这次还顺利吗`
- 管理 -> `这局现在怎么样了`
- 审批 -> `先占位`
- 核销 -> 只在异常兜底里出现
- 海报 -> `最近攒了几个轻松小局`

### 5. 单独点名几个容易摇摆的功能

- 保证金：保留，但前台只说“费用里有一部分是履约约束”，不要让它变成主叙事
- 实名：保留底层能力，但不要做默认高压展示
- 性别限制：只在少数明确场景露出，默认不要变成选局门槛
- 发起人微信号：保留解锁能力，但只在接近见面时轻露出
- 报名审批：默认不要出现在主流程里，能自动就自动
- 扫码核销：只作为补充确认，不做主链路
- 信用分：只做轻信号，不做绩效中心
- 举报：只在异常时出现，不在正常链路里抢存在感
- 日历 / 海报：更适合做个人资产，不适合做首页主卖点

## 30-Day Roadmap

### Week 1: 把“发起”和“加入”做轻

目标：

- 让用户更愿意发
- 让用户更敢报

产品动作：

- 模板广场只保留最轻的主推模板
- 发起页减少“填写感”，更多默认值
- 详情页首屏只回答 5 个问题：
  - 这是什么局
  - 什么时候
  - 在哪
  - 大概要花多少
  - 还差几个人
- 规则说明折叠到底部，不作为首屏重点
- 报名按钮区域文案从“履约/签到/规则”切回“顺手加入”

本周验收：

- 发局完成率
- 详情到报名点击率
- 支付成功率

### Week 2: 把“成局感”做强，但不加重流程

目标：

- 让用户觉得这个局更像真的会发生

产品动作：

- 首页和详情页强化“还差几人”
- 首页新增“今晚可出发”“附近轻松局”模块
- 对标题模糊、地点模糊、时间过远的局降低曝光
- 发起成功后只给一个轻动作建议：`分享给 1 个朋友/群，更容易成局`
- 不做强运营式催促，不做多轮确认

本周验收：

- 成局率
- 平均成局时间
- 差 1 人补位率

### Week 3: 把“结束”改成“再来一次”

目标：

- 提高复购，不增加流程负担

产品动作：

- 战报页弱化“复盘”，强化“一键再来一局”
- 历史记录页增加“再开同款”
- 个人中心增加“最近常玩的局”
- 活动结束后默认只给一个轻问题：
  - `这次还顺利吗？`
- 如果顺利，直接进入“下次再来”承接
- 如果不顺利，再引导到异常反馈

本周验收：

- 战报页到发起页转化率
- 7 日复购率
- 发起人复发率

### Week 4: 做轻裂变，不做重运营

目标：

- 让好局自然传播

产品动作：

- 分享卡只突出：
  - 什么局
  - 几点
  - 在哪
  - 还差几人
  - 大概花多少
- 海报页从“守约月报”转向“最近又攒了几个轻松小局”
- 分享不是任务，不做强引导，只在合适页面给顺手出口
- 不做复杂邀请激励，先看自然分享效果

本周验收：

- 分享率
- 分享到访问转化率
- 分享到报名转化率

## Core Page Principles

### 首页 `pages/index/index`

新原则：

- 像“附近轻松小局流”，不是“活动大厅”
- 少状态，多感觉
- 少规则，多直觉判断

应该强调：

- 今晚可去
- 离我近
- 预算低
- 差几人成局

应该弱化：

- 复杂状态词
- 规则标签堆叠
- 信用信息过载

### 模板广场 `pages/activity/template-select/template-select`

新原则：

- 帮用户快速起意，不要让他做复杂选择

应该强调：

- 哪类局最轻松
- 哪类局最不尴尬
- 哪类局最容易开

应该弱化：

- 模板参数感
- 指标化比较

### 发起页 `pages/activity/create/create`

新原则：

- 像“顺手发个小局”，不是“配置一个活动”

应该强调：

- 默认标题
- 默认时间
- 默认人数
- 默认地点描述

应该弱化：

- 表单长度
- 规则说明密度
- 发起人的管理责任感

### 详情页 `pages/activity/detail/detail`

新原则：

- 像“我要不要一起去”的判断页，不是“报名须知页”

首屏只应该快速传达：

- 这局是干嘛的
- 什么时候见
- 大概花多少
- 还差几个人
- 靠不靠谱

应该弱化：

- 大段规则
- 多块信用信息
- 平台流程说明

### 管理页 `pages/activity/manage/manage`

新原则：

- 发起人不是管理员，只是发起了一个小局的人

应该保留：

- 现在几个人
- 是否快成局
- 能否轻提醒一下

应该删除或隐藏：

- 后台式处理感
- 多层审批感

## 第 3 轮收尾：到场确认页 / 历史页 / 战报页 / 个人中心

这四个页面都只负责承接，不再承担主叙事。

### 到场确认页 `pages/activity/checkin/checkin`

新原则：

- 从“签到页”改成“我到了 / 碰头确认页”

应该强调：

- 我现在离得近不近
- 集合点怎么找
- 到了可以点一下确认

应该弱化：

- 核销感
- 任务感
- 完成流程感

### 历史页 `pages/user/history/history`

新原则：

- 不是历史档案，而是“我最近玩过什么”

应该强调：

- 我发起的局
- 我参与的局
- 再开同款

应该弱化：

- 历史活动
- 参与状态
- 完整流程状态

### 战报页 `pages/activity/report-detail/report-detail`

新原则：

- 不是复盘系统，是“这局不错，下次再来”的承接页

应该强调：

- 这局是什么类型
- 这次顺不顺
- 一键再来
- 分享给朋友

应该弱化：

- 长篇结果页
- 结构化复盘感

### 个人中心 `pages/user/profile/profile`

新原则：

- 用户来这里不是看自己被怎么管理，而是看自己最近玩了什么

应该强调：

- 最近参加的局
- 常玩模板
- 再来一次

应该弱化：

- 高压信用呈现
- 过重的“守约绩效感”

## Metrics Rewritten

轻工具版的核心指标也要重写。

主指标建议变成：

- 发局完成率
- 发局后 24 小时内首个报名率
- 详情页报名点击率
- 支付成功率
- 活动成局率
- 7 日复购率
- 一键同款使用率
- 分享到报名转化率

降级观察指标：

- 到场确认使用率
- 反馈提交率
- 举报率

不建议作为主目标的指标：

- 强制签到完成率
- 评价完成率
- 规则阅读率

因为这些数高，不代表产品更好，只可能代表产品更重。

## New Event/Interaction Philosophy

如果后面继续做埋点，也要按轻工具逻辑收缩：

重点看：

- 用户有没有被吓跑
- 用户有没有顺手发起
- 用户有没有顺手加入
- 用户会不会再回来

少看：

- 用户有没有完成所有流程
- 用户有没有被成功运营触达

埋点重心应该在：

- 浏览
- 点击
- 发起
- 报名
- 成局
- 复用
- 分享

而不是优先压在：

- 签到
- 评价
- 多轮确认

## Open Questions

- 用户到底是更怕被放鸽子，还是更怕“这个产品太正式”？
- 保证金在前台应该被弱化到什么程度，既不吓人，又不失去约束？
- “我到了”这种轻确认，是否足够替代正式签到？
- 对于明显异常场景，怎样做到只影响坏体验用户，不影响正常用户？

## Recommended Next Step

下一步最值得做的，不是继续加新功能，而是做一次“减重式重排”：

1. 列出当前所有主流程功能
2. 给每个功能打标签：
   - 前置
   - 弱化
   - 隐藏
   - 删减
3. 先重写首页、发起页、详情页三处主链路

因为只要这 3 个页面先变轻，整个产品气质就会明显变对。

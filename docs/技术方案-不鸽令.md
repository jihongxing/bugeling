# 技术方案文档 - 不鸽令同城低成本组局平台

> 当前主技术文档。
>
> 本文档描述的是“表层同城低成本组局平台 + 底层线下契约引擎”的整体技术结构，而不是早期单一约见工具的实现。

**版本：** v2.0  
**对应 PRD：** 平台级 PRD（当前版本）  
**技术栈：** 微信小程序 + 微信云开发 CloudBase + 微信支付 + 腾讯地图 + 内容安全能力

---

## 1. 文档目标

`不鸽令` 现在不是一个单层产品。

从技术上看，它由两部分组成：

- 表层产品：同城低成本组局平台，负责模板化供给、附近分发、报名成局、签到评价、活动战报和同款复用
- 底层引擎：线下契约引擎，负责支付、保证金/退款、信用、仲裁、投诉、安全和履约兜底

这份技术方案的目标，是把两层放进同一张图里讲清楚：

1. 当前系统有哪些真实能力
2. 这些能力在代码里如何分层
3. 哪些流程已经落地
4. 哪些旧机制仍然保留，但语义已经升级

---

## 2. 总体架构

### 2.1 分层结构

```text
┌──────────────────────────────────────────────┐
│ 表层产品：同城低成本组局平台                  │
│ 模板发起 / 附近活动流 / 自动成局 / 签到评价    │
│ 活动战报 / 发起同款 / 历史活动 / 内容沉淀      │
└──────────────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────┐
│ 业务编排层：云函数与共享业务模块              │
│ 活动创建 / 活动详情 / 报名支付 / 成局锁局      │
│ 到场签到 / 评价 / 战报生成 / 同款预填          │
└──────────────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────┐
│ 底层引擎：线下契约与风控能力                  │
│ 保证金 / 退款 / 分账 / 信用分 / 自动仲裁       │
│ 内容安全 / 举报 / 冲突检测 / 风险分级          │
└──────────────────────────────────────────────┘
                     │
                     ▼
┌──────────────────────────────────────────────┐
│ 基础设施层                                     │
│ 微信小程序 / CloudBase / 云数据库 / 云存储     │
│ 微信支付 / 腾讯地图 / 微信内容安全 / 生命周期收敛 │
└──────────────────────────────────────────────┘
```

### 2.2 架构原则

1. 表层产品负责提高供给和成局效率。
2. 底层引擎负责降低线下履约风险。
3. 云函数是主要业务边界，前端不直接读写数据库。
4. 历史兼容优先，旧能力尽量做语义升级，而不是粗暴推翻。
5. 风控优先于增长，尤其是夜间、私密空间、转场和投诉场景。

## 3. 业务域划分

当前代码可以按 6 个业务域理解：

### 3.1 活动供给域

职责：

- 模板化发起活动
- 活动列表分发
- 详情页结构化展示
- 从战报复用同款

关键对象：

- `activities`
- `activity_templates`
- `activity_reports_summary`

### 3.2 报名与支付域

职责：

- 创建报名记录
- 支付服务费/保证金
- 支持退款与违约后资金处理

关键对象：

- `participations`
- `transactions`

### 3.3 成局与签到域

职责：

- 根据人数自动成局
- 报名截止后锁局
- 到场签到、扫码核验、手动确认

关键对象：

- `activities.status`
- `participations.status`

### 3.4 信用与评价域

职责：

- 信用分与访问控制
- 活动后互评
- 正负标签沉淀

关键对象：

- `credits`
- `activity_reviews`

### 3.5 风控与投诉域

职责：

- 内容安全
- 举报存证
- 自动仲裁
- 风险等级与高风险活动治理

关键对象：

- `reports`
- `moderation_tasks`

### 3.6 内容沉淀与复用域

职责：

- 生成活动战报
- 战报摘要落库
- 发起同款预填

关键对象：

- `activity_reports_summary`
- `activities.sourceReportId`

## 4. 前端架构

### 4.1 页面分组

当前小程序前端主要分为 5 组页面：

```text
pages/
├── index/                       # 首页活动流
├── activity/
│   ├── create/                  # 模板化发起
│   ├── detail/                  # 活动详情
│   ├── checkin/                 # 到场签到
│   ├── review/                  # 活动互评
│   ├── report-detail/           # 活动战报
│   └── template-select/         # 模板选择
├── verify/
│   ├── qrcode/                  # 核销码，兼容补充履约
│   └── scan/                    # 发起人扫码，兼容补充履约
├── user/
│   ├── profile/                 # 个人中心
│   ├── history/                 # 历史活动
│   ├── calendar/                # 日历
│   └── poster/                  # 海报
└── report/                      # 举报页
```

### 4.2 页面职责变化

相比旧的契约工具，几个页面的语义已经变化：

- `activity/create` 从“手写约见表单”升级为“模板化低成本组局发起页”
- `activity/detail` 从“契约详情页”升级为“结构化活动详情页”
- `verify/*` 仍保留，但从主履约入口降级为补充核验手段
- `user/history` 不再只是历史履约记录，也承担战报入口
- `activity/report-detail` 和 `createActivityFromReport` 构成增长闭环

### 4.3 前端设计原则

1. 首页优先帮用户判断“值不值得去”
2. 创建页优先减少空白输入
3. 详情页优先明确成局条件、安全条件、费用结构
4. 战报页优先承担内容沉淀和复用，而不是单纯展示

### 5.4 信用、评价与安全域

## 6. 数据模型

### 6.1 activities

当前 `activities` 已从“单次约见记录”演化为“结构化组局活动”。

关键字段：

| 字段 | 说明 |
|------|------|
| `templateType` / `templateVersion` | 活动模板信息 |
| `title` / `summary` / `description` | 标题、摘要、结构化说明 |
| `budgetType` / `budgetMin` / `budgetMax` | 预算语义 |
| `serviceFee` / `bondAmount` / `depositTier` | 支付结构，兼容旧押金语义 |
| `minParticipants` / `maxParticipants` | 成局与人数上限 |
| `approvedParticipants` / `currentParticipants` / `waitlistCount` | 当前人数信息 |
| `location` / `locationName` / `locationAddress` | 地点与 POI |
| `meetTime` / `signupDeadline` | 活动时间与报名截止 |
| `startCheckinAt` / `endCheckinAt` | 签到窗口 |
| `meetingPointText` / `identityHint` | 集合与接头说明 |
| `realNameRequired` / `genderLimit` / `allowAfterParty` | 安全与筛选开关 |
| `safetyTags` / `atmosphereTags` | 展示与风控标签 |
| `riskLevel` / `reviewStatus` | 风险等级与审核结果 |
| `status` | 活动状态机字段 |
| `sourceReportId` | 同款复用来源战报 |

### 6.2 participations

`participations` 不再只是“支付后等待审批”，而是完整参与链路。

关键字段：

| 字段 | 说明 |
|------|------|
| `activityId` / `participantId` | 关联关系 |
| `status` | `pending_payment / paid / confirmed / waitlisted / checked_in / completed / cancelled / breached` |
| `serviceFeeAmount` / `bondAmount` | 费用拆分 |
| `refundStatus` | 退款状态 |
| `signupSource` | 报名来源，如 `report_reuse` |
| `checkinMethod` / `checkinAt` / `checkinLocation` | 签到信息 |
| `ratingSubmitted` | 是否已完成互评 |

### 6.3 credits

信用模型现在同时服务“履约控制”和“平台分发信任”。

建议/现有字段包括：

| 字段 | 说明 |
|------|------|
| `score` | 当前信用分 |
| `totalInitiated` / `totalJoined` / `totalCompleted` | 活动累计统计 |
| `totalNoShow` / `totalComplaints` | 风险统计 |
| `positiveTags` / `negativeTags` | 标签沉淀 |
| `realNameVerified` | 是否实名 |
| `creditLevel` | 用户信用等级 |

### 6.4 其他集合

| 集合 | 作用 |
|------|------|
| `transactions` | 支付、退款、分账流水 |
| `reports` | 举报记录 |
| `activity_reviews` | 活动互评 |
| `activity_templates` | 模板配置 |
| `activity_reports_summary` | 活动战报摘要与同款复用源 |
| `moderation_tasks` | 风控审核任务 |

### 6.5 兼容策略

系统仍处于升级过程，文档必须承认这一点：

- `depositTier` 仍保留，作为旧押金语义兼容字段
- 二维码核销链路仍保留，作为定位签到失败时的补充机制
- 部分旧状态与新状态会在接口层做映射，而不是一次性清空历史数据

## 7. 状态机设计

### 7.1 活动状态机

目标状态机：

```text
recruiting
  ↓ 达到最低成局人数
formed
  ↓ 到报名截止
locked
  ↓ 到活动开始
in_progress
  ↓ 完成签到、评价、结算
finished

异常分支：
- cancelled
- pending_review
- removed
```

兼容映射：

| 旧状态 | 当前语义 |
|--------|----------|
| `pending` | `recruiting` |
| `confirmed` | `formed` 或 `locked` |
| `verified` | `finished` |
| `expired` / `settled` | `finished` 或异常结算完成 |

### 7.2 参与状态机

```text
pending_payment
  ↓ 支付成功
paid
  ↓ 成局确认
confirmed
  ↓ 到场签到
checked_in
  ↓ 活动结束 + 评价完成
completed

异常分支：
- waitlisted
- cancelled
- breached
- refunded
```

### 7.3 为什么保留旧链路

这是一个现实工程选择。

当前项目已经有成熟的押金、退款、核销、仲裁代码。如果为了语义纯洁全部推翻，风险会非常高。更合理的做法是：

- 表层先升级产品语义
- 底层逐步吸收旧能力
- 在接口层做兼容

## 8. 关键业务流程

### 8.1 模板发起与同款复用

```text
用户选择模板
  ↓
createActivity / previewActivityDraft
  ↓
生成结构化活动
  ↓
若来自战报复用：
report-detail → createActivityFromReport
  ↓
生成 seed 并写入 sourceReportId
```

关键点：

- 发起页尽量减少自由输入
- 战报复用优先继承模板、预算、人数、安全配置
- 用户主要修改时间和地点

### 8.2 报名支付与自动成局

```text
用户查看活动详情
  ↓
createDeposit
  ↓
payCallback
  ↓
participation.status = paid
  ↓
autoFormActivity
  ↓
人数达标后进入 formed
```

关键点：

- 支付金额由服务费 + 保证金构成
- 发起人审批不再默认阻塞所有活动
- 高风险活动仍可保留审批或审核

### 8.3 签到、核验与结算

```text
活动开始前开放签到
  ↓
reportArrival
  ↓
定位成功 → checked_in
  ↓
必要时 manualVerify / verifyQrToken 补充核验
  ↓
活动结束后退款或异常处理
```

关键点：

- 主流程是定位签到
- 二维码与扫码核销降级为补充履约手段
- 仲裁与退款仍依赖底层契约引擎

### 8.4 评价、战报与增长闭环

```text
活动结束
  ↓
submitActivityReview
  ↓
generateActivityReport
  ↓
activity_reports_summary 落库
  ↓
report-detail 展示
  ↓
createActivityFromReport 发起同款
```

关键点：

- 战报不是装饰，它是供给复用接口
- `activity_reports_summary` 同时服务展示和 seed 生成
- 这条链路是平台增长闭环的核心

## 9. 风控与安全设计

### 9.1 内容安全

- 文本走 `msgSecCheck`
- 图片走图片安全检测
- 举报支持图片 + LBS 存证
- 高风险描述、私密空间、暗示性表达优先拦截

### 9.2 线下安全边界

- 默认公共空间见面
- 弱化私聊，微信号解锁不再是主流程
- 不鼓励私宅、深夜、一对一高风险场景
- 风险等级决定活动是否进入 `pending_review`

### 9.3 资金合规

- 服务费和保证金分离
- 退款、分账都走微信原路
- 不沉淀自有余额池，避免二清风险

### 9.4 仲裁与信用

- 自动仲裁优先规则化
- 极端投诉场景才引入人工
- 信用系统不仅限制访问，也会影响活动信任感和后续分发

## 10. 基础设施与运维

### 10.1 云开发资源

- 云数据库：活动、报名、评价、举报、战报摘要
- 云函数：业务主入口
- 云存储：举报图、活动补充图片

### 10.2 外部依赖

- 微信支付：支付、退款、分账
- 腾讯地图：POI 与 LBS
- 微信内容安全：文本、图片审核

### 10.3 生命周期收敛

当前版本已移除高频定时任务，改为“单活动事件驱动 + 懒执行收敛”：

| 触发点 | 作用 |
|------|------|
| `getActivityDetail` | 读取前补齐锁局、仲裁、分账、退款重试 |
| `approveParticipant` | 审批前后补齐锁局与状态推进 |
| `payCallback` | 支付完成后补齐成局/锁局相关状态 |
| `reportArrival` / `verifyQrToken` / `manualVerify` | 到场与核销动作后补齐仲裁与退款重试 |

兼容说明：

- `autoArbitrate`、`executeSplit`、`processVerifiedRefunds`、`autoLockActivities` 仍保留为兼容入口
- 这些云函数不再绑定高频 timer，主要用于人工补处理或历史数据排查

### 10.4 测试策略

项目当前采用：

- 单元测试：覆盖云函数、共享模块、前端辅助函数
- 属性基测试：覆盖状态机、支付金额不变量、时间/距离等规则

测试目标不是只验证 demo path，而是确保底层契约引擎在异常场景下仍可靠。

## 11. 当前实现状态与后续演进

### 11.1 已落地能力

- 模板化创建活动主链路
- 活动结构化详情页
- 低成本费用结构与创建参数
- 报名支付、退款、分账、信用、投诉
- 到场签到与补充核验
- 互评、战报生成、战报落库、发起同款
- 历史活动、日历、海报、冲突检测

### 11.2 仍在演进的部分

- 更完整的模板系统运营能力
- 更清晰的 formed / locked / in_progress 状态统一
- 更强的推荐排序与内容流分发
- 更细粒度的风控审核后台

### 11.3 结论

`不鸽令` 的技术核心已经不是“一个押金工具页面接几个支付接口”。

它现在更接近一个：

- 以组局供给为表层产品
- 以履约、风控和资金规则为底层护城河
- 以战报复用驱动供给增长

的轻量同城活动平台。

# UI/交互规范 - 不鸽令同城低成本组局平台

> 当前主 UI 规范。
>
> 本文档描述的是升级后的平台级界面规范，适用于“表层同城低成本组局平台 + 底层线下契约引擎”的产品结构，不再只是早期契约工具页面说明。

---

## 1. 设计目标

这套 UI 不是在卖“社交幻想”，而是在帮助用户快速判断：

1. 这是什么局
2. 要花多少钱
3. 几个人才能成
4. 安不安全
5. 现在能不能报

所以视觉和交互的目标必须很明确：

- 降低发起门槛
- 降低报名犹豫
- 提高安全感
- 让战报与同款复用自然发生

---

## 2. 产品层级与界面心智

当前产品有两层心智：

- 表层产品：同城低成本组局平台
- 底层能力：线下履约与风控引擎

界面上不要把“底层规则”做成主叙事，但必须在关键节点让用户感知到它存在。

表现方式：

- 首页和模板页讲“低成本、附近、可成局”
- 详情页和支付页讲“费用结构、规则、安全”
- 签到与举报页讲“到场记录、争议处理”
- 战报页讲“复盘、复用、继续发起”

---

## 3. 设计原则

### 3.1 先判断，再行动

每个核心页面都要先帮用户判断，再让用户点击。

比如详情页里，优先展示：

- 模板类型
- 时间地点
- 预算
- 成局进度
- 服务费 + 保证金
- 安全条件

不要一上来就把 CTA 做得很大，但关键信息藏起来。

### 3.2 轻松感和规则感同时存在

这不是冷冰冰的风控后台，也不是暧昧聊天软件。

界面气质应同时具备：

- 出门前的轻松感
- 履约规则的明确感

也就是，页面可以轻，但规则不能糊。

### 3.3 结构化优先

尽量少依赖大段自由文案。

优先用这些元素表达信息：

- 标题
- 标签
- 指标
- 分组卡片
- 状态按钮
- 摘要句

### 3.4 强调“公共空间、低预算、弱关系”

这三个词要持续出现在视觉和文案里。

无论是模板页、详情页还是规则页，都应该强化：

- 公共空间
- 低成本
- 可退出
- 不强制社交

### 3.5 战报不是装饰页

活动战报页要被当成增长页面，而不是简单结果页。

它必须承担：

- 回顾活动
- 展示模板价值
- 触发同款复用

所以“发起同款”不是附属按钮，而是主动作之一。

## 4. 视觉系统

### 4.1 色彩规范

| 用途 | 色值 | 说明 |
|------|------|------|
| 主色 | `#FF6B35` | 品牌主色，强调按钮、主标签、关键 CTA |
| 深色文字 | `#1A1A1A` | 页面主标题、正文重点 |
| 次级深色 | `#2D3748` | 卡片标题、数据说明 |
| 成功色 | `#10B981` | 已签到、信用稳定、成功反馈 |
| 警告色 | `#F59E0B` | 倒计时、待处理、临界成局 |
| 危险色 | `#EF4444` | 举报、违约、高风险提示 |
| 背景色 | `#F7F4EF` | 页面大背景，带一点暖灰感，避免冷白 |
| 卡片底色 | `#FFFFFF` | 主卡片背景 |
| 分割线 | `#E8E1D8` | 轻分割 |
| 辅助文字 | `#6B7280` | 次要说明、描述、空状态辅助文案 |

### 4.2 颜色使用原则

- 橙色只给真正重要的动作和结果，不要到处刷主色
- 红色只用于风险和异常，不要拿来装饰
- 绿色用于“已经完成/可信赖”，不能泛滥
- 大面积背景避免纯白，应该让产品更像“真实城市生活工具”，不是管理后台

### 4.3 字体规范

现阶段优先沿用小程序系统字体，保证兼容性和开发效率。

## 5. 核心组件规范

### 5.1 活动卡片 `activity-card`

活动卡片是首页最重要的组件。

必须包含：

- 活动标题
- 模板标签
- 时间
- 距离
- 人数进度
- 模板预算
- 服务费/保证金摘要
- 发起人信用摘要
- 安全标签

视觉要求：

- 标题占据第一视线
- 标签行不要超过两行
- 预算与费用信息要和“人均花费”区分开
- “快成局”状态可以用轻微强调色，但不能造成恐慌式营销

### 5.2 Hero 卡片

当前首页、模板广场、创建页、规则页、战报页都使用 Hero 风格。

结构建议：

- `hero-kicker`
- `hero-title`
- `hero-desc`
- 标签或摘要指标
- 主 CTA / 次 CTA

作用：

- 建立页面气质
- 快速解释当前页在做什么

### 5.3 费用拆解组件

适用于详情页、创建页、报名页。

必须分开表达：

- 人均预算
- 服务费
- 保证金

禁止把所有数字混成一句模糊文案。

### 5.4 安全标签组件

建议以标签形式展示，例如：

- `公共空间`
- `低预算`
- `实名优先`
- `仅女生`
- `不转场`

原则：

- 标签越少越好，但必须稳定
- 优先展示能降低犹豫的信息

### 5.5 成局进度组件

适用于详情页和首页卡片。

需要至少支持：

- 当前人数 / 成局线 / 上限
- 是否快成局
- 是否已成局

视觉上建议用：

- 数字 + 轻量进度条
- 或数字 + 状态短句

不要做成重图表。

## 6. 页面级交互规范

### 6.1 首页 `pages/index`

定位：

- 活动发现页
- 不是信息流社区
- 不是聊天入口

页面结构建议：

1. 顶部 Hero
2. 当前城市/附近说明
3. 快速筛选
4. 活动列表
5. 空状态或加载更多

首屏必须优先展示：

- 附近有多少个局接近成局
- 有多少个预算友好
- 模板化发局的心智

交互要求：

- 下拉刷新
- 上拉分页
- 卡片点击进详情
- 筛选切换时不打断浏览心流

### 6.2 模板广场 `pages/activity/template-select`

定位：

- 把“从零发起”变成“选一个就能发”

页面重点：

- 推荐公共空间、低预算、轻负担模板
- 模板卡片必须能让用户立刻理解玩法
- 每个模板都要有明确 action，例如“用这个模板发起”

交互要求：

- 当前已选模板要明显区分
- 推荐标签不要滥用，避免每个都是“推荐”

### 6.3 发起页 `pages/activity/create`

定位：

- 从空白输入页，升级为低摩擦编排页

页面结构建议：

1. Hero 引导
2. 模板选择
3. 活动信息
4. 预算与费用
5. 安全和集合说明
6. 发布按钮

关键要求：

- 预算、保证金、安全条件必须结构化
- 不要让用户觉得自己在填复杂后台表单
- 如果来自战报复用，要有明显的 `prefill-banner`

同款复用场景提示文案原则：

- 告诉用户哪些内容已带入
- 明确只需要改时间地点

### 6.4 活动详情页 `pages/activity/detail`

定位：

- 报名前的判断页

页面信息优先级：

1. 标题、模板类型、时间地点
2. 人均预算、费用结构、人数进度
3. 活动说明
4. 安全条件
5. 发起人信用
6. CTA

按钮逻辑必须清晰：

- 未报名：显示报名 CTA
- 发起人：显示管理 CTA
- 已报名：显示状态或签到入口
- 已结束：显示战报入口

细节要求：

- 风险提示不要喧宾夺主，但必须存在
- 支付说明必须明确“保证金按规则处理”

### 6.5 签到页 `pages/activity/checkin`

定位：

- 到场确认页

页面必须清楚回答：

- 现在能不能签到
- 签到窗口是什么
- 当前距离集合点多远
- 点击后会发生什么

推荐结构：

1. 当前签到状态
2. 签到信息
3. 距离反馈
4. 签到说明
5. 主按钮

交互要求：

- 权限申请要解释“为何要获取定位”
- 成功反馈要明确“已记录到场”
- 超过建议签到时段也要给补签路径，不要直接把人锁死

### 6.6 活动互评页 `pages/activity/review`

定位：

- 快速总结体验

原则：

- 正向标签和负向标签分开
- 不强迫写长评论
- 提交规则透明

视觉要求：

- 标签选项点击反馈清晰
- 当前已选状态明显
- 提交后给用户“已记录，会进入后续信用统计”的确定感

### 6.7 活动战报页 `pages/activity/report-detail`

定位：

- 内容沉淀页
- 复用转化页

页面结构建议：

1. Hero：活动战报
2. 核心指标：人数、预算、费用、集合点
3. 摘要信息
4. 安全标签
5. 复用 CTA

视觉要求：

- 战报页应比详情页更“像成果页”
- 但不能空洞，要让人看完立刻知道“这局是怎么做出来的”

关键动作：

- `发起同款` 是主 CTA
- CTA 上方必须有一句解释为什么这个模板可继续用

### 6.8 历史活动页 `pages/user/history`

定位：

- 复盘页，不只是列表归档

每条历史记录应尽量提供：

- 当前状态
- 是否已评价
- 战报入口

目标：

- 帮用户回看自己的活动资产
- 把战报入口做成自然延伸

### 6.9 规则页 `pages/rules`

定位：

- 平台边界说明页

内容结构应分块：

- 产品适合什么局
- 费用与保证金规则
- 签到与履约规则
- 安全边界

写法要像“帮你避坑”，不要像平台官话。

### 6.10 个人中心 / 日历 / 海报

这三页共同承担“用户资产感”：

- 个人中心：信用与身份入口
- 日历：活动履约轨迹
- 海报：可分享的信用/出门资产

注意：

- 这些页面现在仍有较强的“契约工具”遗产
- 后续升级时，应该逐步从“守约展示”过渡到“组局资产展示”

## 7. 状态与文案系统

### 7.1 活动状态标签

建议统一映射以下视觉语义：

| 状态 | 颜色倾向 | 文案建议 |
|------|----------|----------|
| `recruiting` / `pending` | 黄橙 | 招募中 |
| `formed` / `confirmed` | 蓝绿 | 已成局 |
| `locked` | 深蓝灰 | 已锁局 |
| `in_progress` | 绿色 | 进行中 |
| `finished` / `verified` | 绿色 | 已结束 |
| `cancelled` | 灰色 | 已取消 |
| `breached` | 红色 | 违约 |

### 7.2 文案原则

- 少用“契约”做主话术，多用“活动”“组局”“签到”“同款”
- “保证金”比“鸽子费”更适合当前平台主文案
- 风险文案要直接，不要委婉到看不懂

示例：

- 好：`报名需先支付服务费和保证金，守约后按规则处理`
- 差：`参与本活动可能产生一定费用，请谨慎操作`

## 8. 动效与反馈

### 8.1 动效原则

- 少，但有用
- 重点用于状态切换和结果确认
- 不做花哨过场

### 8.2 推荐动效场景

| 场景 | 动效 |
|------|------|
| 页面首屏 | Hero 轻微上浮进入 |
| 模板选中 | 卡片边框/阴影切换 |
| 签到成功 | 主按钮状态切换 + 成功提示 |
| 发起同款跳转 | CTA 按钮按压反馈 |
| 提交互评 | 提交完成后结果卡显现 |

### 8.3 Toast / Modal 规范

- Toast 用于短反馈：成功、失败、保存、复制
- Modal 用于不可逆或高风险提醒：冲突、超时、风险提示
- 不要把所有东西都塞给 Toast

## 9. 空状态与异常状态

### 9.1 空状态

| 场景 | 文案方向 |
|------|----------|
| 附近暂无活动 | 去发起一个低成本局 |
| 没有历史活动 | 第一场活动会从这里开始 |
| 没有战报 | 活动结束后会在这里沉淀战报 |
| 模板未命中 | 先试试最接近的推荐模板 |

### 9.2 异常状态

| 场景 | 处理原则 |
|------|----------|
| 网络异常 | 给重试按钮 |
| 页面加载失败 | 明确失败，不假装空数据 |
| 定位失败 | 解释权限原因，并保留补救路径 |
| 战报拉取失败 | 允许展示本地摘要兜底 |

## 10. 可访问性与实现约束

### 10.1 小程序实现约束

- 优先使用稳定的原生组件
- 保证 Android / iOS 视觉一致性
- 避免过度依赖复杂自定义动画

### 10.2 触控与阅读

- 可点击区域不要太小
- 核心按钮高度应足够明显
- 关键信息避免堆叠成密集说明文字

### 10.3 数据缺失兜底

当字段不完整时，页面应有可读兜底：

- 预算缺失：`预算待补充`
- 人数未知：`待确认`
- 集合点缺失：`待补充`

不要出现大片空白。

## 11. 当前页面与后续演进

### 11.1 已经形成的平台级视觉模式

当前代码里已经稳定出现的模式：

- Hero 卡片
- 分段 Section 卡片
- 强调预算与费用拆解
- 安全标签
- 战报页复用 CTA
- 创建页预填 Banner

这说明产品已经不再是单页契约工具，而是在向“结构化活动平台”靠拢。

### 11.2 后续 UI 升级重点

接下来最值得继续统一的 4 个点：

1. 首页活动卡片与详情页的信息层级完全对齐
2. 日历/海报从“契约展示”升级成“活动资产展示”
3. 签到、扫码、人工确认三条履约链路的视觉语义统一
4. 战报页和同款发起页做成更完整的增长闭环

### 11.3 结论

这套 UI 规范服务的，已经不是一个“见面前交押金”的单点工具。

它服务的是一个：

- 更容易发起
- 更容易判断
- 更容易成局
- 更容易复用

的同城低成本组局平台。
